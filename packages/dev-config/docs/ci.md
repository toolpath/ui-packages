# Shared CI

`@toolpath/dev-config` ships its CI as a product surface. One central reusable workflow and three composite actions in `toolpath/ui-packages` run the whole quality contract. A consumer repository keeps only a small generated caller with its repository facts. It does not copy lint, type, test, or setup shell into each repository.

| Piece            | Path in `toolpath/ui-packages`                  | Role                                                                                   |
| ---------------- | ----------------------------------------------- | -------------------------------------------------------------------------------------- |
| Central workflow | `.github/workflows/dev-config-quality.yml`      | `workflow_call`: diagnosis, plan, standards stages, central suites, verification       |
| Setup action     | `.github/actions/dev-config-setup`              | Pinned Node and package manager, store cache, frozen install, browsers, `doctor`, plan |
| Check action     | `.github/actions/dev-config-check`              | Runs one declared stage or `project:suite` and proves it with a receipt                |
| Result action    | `.github/actions/dev-config-result`             | Dependency-free verification of jobs and receipts (`runs: node24`)                     |
| Caller           | `.github/workflows/quality.yml` in the consumer | Generated by `toolpath-dev init`, updated by `toolpath-dev sync`                       |

Run the same contract locally with `toolpath-dev ci`. It runs the read-only format backstop, lint, types, and unit suites, then each required central suite, and lists delegated and manual suites. `toolpath-dev ci --plan` prints the execution plan the workflow schedules.

## The caller

`toolpath-dev init` writes the caller and `toolpath-dev sync` keeps it current, so it is never edited from scratch. For a repository with one delegated suite it looks like this:

```yaml
name: Quality

on:
  pull_request:
  push:
    branches:
      - main
  merge_group:

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow_ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  standards:
    uses: toolpath/ui-packages/.github/workflows/dev-config-quality.yml@<release source SHA>
    with:
      working-directory: .

  app-integration:
    name: app:integration
    runs-on: ubuntu-24.04
    timeout-minutes: 30
    outputs:
      receipt: ${{ steps.check.outputs.receipt }}
    steps:
      - uses: actions/checkout@<pinned SHA> # v7.0.1
        with:
          persist-credentials: false
      - uses: toolpath/ui-packages/.github/actions/dev-config-setup@<release source SHA>
        with:
          working-directory: .
      # Application setup for app:integration belongs here and is owned by this repository.
      - id: check
        uses: toolpath/ui-packages/.github/actions/dev-config-check@<release source SHA>
        with:
          working-directory: .
          suite: app:integration
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}

  quality:
    name: quality
    if: always()
    needs:
      - standards
      - app-integration
    runs-on: ubuntu-24.04
    timeout-minutes: 5
    steps:
      - uses: toolpath/ui-packages/.github/actions/dev-config-result@<release source SHA>
        with:
          needs: ${{ toJSON(needs) }}
          required: |
            [
              {"kind":"standards","job":"standards"},
              {"kind":"suite","job":"app-integration","suite":"app:integration"}
            ]
```

- **Triggers.** Pull requests, pushes to the default branch, and the merge queue. Never `pull_request_target` or `workflow_run`, which run repository code with privileged credentials.
- **Permissions.** Only `contents: read`. The standards job needs no secrets, so it runs on pull requests from forks.
- **Concurrency.** One group per workflow file and ref (`github.workflow_ref` names the repository, the workflow, and the ref). A newer push cancels an older run of the same pull request. Default-branch and merge-queue runs are never cancelled, and other workflows, including release jobs, are in other groups.
- **`standards`** calls the central workflow at the full source SHA of the installed `@toolpath/dev-config` release. It takes no `secrets: inherit`.
- **Delegated suite jobs.** There is one per `ci.externalSuites` entry in `dev.config.mjs`. The suite needs services, simulators, or credentials the central workflow cannot provide, so the repository owns that setup between the setup and check steps. Only the environment variables the suite declares in `prerequisites.env` are mapped, each from its own named secret. Replace a mapping with `vars.` when the value is not a secret.
- **`quality`** always runs. It passes only when `standards` and every delegated job succeeded and published a verified receipt. This is the check branch protection requires.

Your edits to the caller are kept on `sync` where they do not overlap the generated changes. Typical edits are a service container, setup steps, or a different runner for a native job. `toolpath-dev doctor` reports an edit that breaks the contract: a mutable reference, a reference from another release, a delegated suite missing from `quality`, `secrets: inherit`, or a privileged trigger.

## What the central workflow runs

The central workflow's inputs are repository facts only: `working-directory` (default `.`) and an optional `config` path. It accepts no rule maps, skip flags, or shell.

1. **`standards`** (20 minutes, `ubuntu-24.04`):
   - Checks out the consumer, then this workflow's own source at `.toolpath/ci-source`. The source comes from `job.workflow_repository` at `job.workflow_sha`, with `persist-credentials: false`. Local actions resolve from that literal path. `github.repository` and `github.sha` would name the caller, and a moving branch would not match the release.
   - The setup action selects the pinned Node and package manager, restores the store cache, installs with the frozen lockfile (`pnpm install --frozen-lockfile` or `npm ci`) without hooks, runs `toolpath-dev doctor`, and computes the plan.
   - The check action runs the read-only format backstop, lint, types, and unit suites in one invocation, so prerequisite builds run once.
2. **`suites`** runs each required browser or command suite in its own matrix job: at most two at a time, no fail-fast, with the suite's own timeout. It runs only when the plan has such suites. Browser jobs install only the browsers their suite declares. A Playwright suite that is `ci: 'manual'` is not scheduled at all; suites in `ci.externalSuites` run in the caller.
3. **`verify`** always runs. It downloads the receipts and checks them with the result action against the plan. It publishes the verified summary that the caller's `quality` job reads as the workflow's `receipt` output.

The plan is deterministic. It derives from `dev.config.mjs` alone: stages, unit suites, prerequisite builds in dependency order, central suites, delegated suites, and manual suites with their reasons.

## Receipts and failure semantics

Every stage and suite writes a receipt: the id, a `passed`, `failed`, or `error` status, the duration, test counts for test stages, a one-line message on failure, and the package identity. Receipts never contain logs, file contents, or secrets. A zero exit code is not evidence. A test stage passes only when its runner's report shows executed tests and no failures, and a suite that discovered no tests fails.

The result policy is one dependency-free module, `src/ci/result-policy.mjs`. The packaged CLI and the result action import the same file. The result action runs from its own checkout, so it still reports when a consumer's install failed. The policy fails on any of these:

- a required job that finished `failure` or `cancelled`, or was unexpectedly `skipped`;
- a job missing from `needs`, or a job in `needs` that the generated inventory does not list;
- a missing, malformed, or failed receipt, or a receipt the plan does not require;
- unit suites that differ from the ones the plan declares;
- a suite the central plan delegates to a caller job that the caller's inventory does not require. Adding a suite to `ci.externalSuites` without running `sync` fails here and in `doctor`.

Manual suites (`ci: 'manual'` with a reason) leave the inventory before anything runs. They are listed as notices in every summary rather than inferred from a skipped job.

## Specialized jobs

The caller jobs below are generic examples. The application setup between the setup and check steps belongs to the repository; the check step is always the shared action, which runs the suite declared in `dev.config.mjs` and verifies its receipt.

A service-backed suite with a database container:

```yaml
api-integration:
  name: api:integration
  runs-on: ubuntu-24.04
  timeout-minutes: 30
  services:
    postgres:
      image: postgres:17
      env:
        POSTGRES_PASSWORD: postgres
      ports:
        - 5432:5432
      options: >-
        --health-cmd "pg_isready" --health-interval 5s --health-timeout 5s --health-retries 10
  outputs:
    receipt: ${{ steps.check.outputs.receipt }}
  steps:
    - uses: actions/checkout@<pinned SHA> # v7.0.1
      with:
        persist-credentials: false
    - uses: toolpath/ui-packages/.github/actions/dev-config-setup@<release source SHA>
    - name: Apply the schema
      run: node scripts/migrate.mjs
      env:
        DATABASE_URL: postgres://postgres:postgres@localhost:5432/postgres
    - id: check
      uses: toolpath/ui-packages/.github/actions/dev-config-check@<release source SHA>
      with:
        suite: api:integration
      env:
        DATABASE_URL: postgres://postgres:postgres@localhost:5432/postgres
```

A native command suite on a macOS runner, declared in `dev.config.mjs` as `runner: 'command'` with `argv`, a `report`, and `prerequisites: { commands: ['xcrun'] }`:

```yaml
mobile-simulator:
  name: mobile:simulator
  runs-on: macos-15
  timeout-minutes: 30
  outputs:
    receipt: ${{ steps.check.outputs.receipt }}
  steps:
    - uses: actions/checkout@<pinned SHA> # v7.0.1
      with:
        persist-credentials: false
    - uses: toolpath/ui-packages/.github/actions/dev-config-setup@<release source SHA>
    - name: Boot a simulator
      run: xcrun simctl boot "iPhone 16"
    - id: check
      uses: toolpath/ui-packages/.github/actions/dev-config-check@<release source SHA>
      with:
        suite: mobile:simulator
```

The check action accepts a declared stage (`standards`, `format`, `lint`, `types`, `unit`) or a `project:suite` identifier, never a command. A command suite runs the `argv` from `dev.config.mjs` without a shell, after its declared prerequisites are checked. A step that exits zero without producing the suite's declared report fails.

Credential-dependent suites need a deliberate strategy for pull requests from forks, which receive no secrets: the job fails rather than passing without its credentials. Common choices are running such a job only on `merge_group` and `push`, or keeping it `ci: 'manual'` with a reason.

## Branch protection

Require the caller's **`quality`** check. After the workflow's first run, the pull request's checks list shows it as `Quality / quality`. In repository rulesets or branch protection, the required status check name is `quality`. Do not require the individual `standards / …` jobs, whose names follow the central workflow's structure. Changing rulesets or branch protection is a separate administrative action; adopting the package does not do it.

## Caching, logs, and artifacts

- The package manager's store is cached under a key of OS, architecture, Node version, package manager and version, and the lockfile's SHA-256. `node_modules` is never cached, and the install always runs with the frozen lockfile.
- Playwright browsers are cached by OS, architecture, and the exact installed `@playwright/test` version. Installation still runs (`playwright install --with-deps`) on a cache hit.
- No typed ESLint result cache and no cached success receipts. Every run checks afresh.
- A passing stage prints one line. Failures print the tool's own diagnostic immediately. Each check step writes a Markdown table of its receipts to the job summary.
- On failure the check action uploads the runner reports, Playwright traces and screenshots, and the receipts for 7 days. Hidden files, `.env` files included, are never uploaded. Receipts for verification are uploaded on every run, also for 7 days.

## Release identity

Each build writes `dist/release.json` with the package version, the exact toolchain, the repository, and the full commit SHA it was built from. A release build refuses a dirty source tree, and a commit that does not record the version being packed. `init` and `sync` write that SHA into every `uses:` reference of the caller and record it in `.toolpath/dev-config.json`. `doctor` compares the installed package, the receipt, and the caller, so package and CI policy always upgrade together in one consumer PR. No mutable major tag or registry lookup is involved.

A development build (a local or PR build) records `channel: "development"`, and `init`/`sync` refuse it. Before the first npm release, `.github/workflows/dev-config-selftest.yml` proves the actions anyway: it packs the package with a release identity naming the run's own revision and installs it into disposable npm and pnpm consumers. It then runs the real setup, check, and result actions against them. That override exists only in the selftest harness, `scripts/ci-selftest.mjs`.

## Maintaining the CI

- **Action pins.** Every third-party action is pinned to a full commit SHA with its tag as a comment. `src/ci/pins.json` is the only registry. To move a pin, resolve the release tag's commit with `gh api` (dereferencing an annotated tag), update `pins.json`, and run `node scripts/sync-action-pins.mjs`. `tests/ci` fails when a workflow or action disagrees with the registry or contains a mutable reference.
- **actionlint.** The selftest validates both workflows with the official `rhysd/actionlint` release binary. The binary is pinned in `pins.json` and checked against its published SHA-256. Version 1.7.12 predates GitHub's documented `job.workflow_repository`, `job.workflow_sha`, `job.workflow_ref`, and `job.workflow_file_path` properties. That one message is ignored with a narrow pattern; every other check applies. Remove the ignore once a release knows these properties.
- **Generated callers.** `src/ci/render.ts` renders callers and `callerWorkflowIssues` checks them. Change both together, and cover the rendering in `tests/ci/render.test.ts`.

## Limits

- **GitHub.com only.** The central workflow relies on `job.workflow_repository` and `job.workflow_sha`, which GitHub Enterprise Server does not provide.
- **One runner image.** Generic jobs run on `ubuntu-24.04`. Delegated jobs choose their own runner in the caller.
- **The reusable workflow end to end.** It runs only when a consumer repository calls it. This repository's selftest executes the setup, check, and result actions and the plan against real installed consumers, and validates the workflow statically, but cannot call the workflow against a consumer of its own.
- **TypeScript `include` globs.** The central source checkout lives at `.toolpath/ci-source` inside the workspace. A consumer `tsconfig.json` that includes everything (`"include": ["**/*"]`) without excluding `.toolpath` would type-check that checkout too. Include the source directories explicitly, as the package presets assume.
